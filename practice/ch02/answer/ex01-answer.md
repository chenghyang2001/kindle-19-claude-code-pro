# 練習 01 解答 — 重寫低效提示詞

> 實驗環境：Claude Code 2.1.302、`claude -p --tools ""`（純文字回答、不給工具）、每次 timeout 120 秒、2026-10-18 實跑。
> 原始輸出：`outputs/ex01-*.md`；量化指標：`outputs/metrics-ex01-ex02.json`；驗證：`tests/test_outputs.py`。

## 任務 1：診斷問題

### ①「幫我改一下這個 function」

| 面向 | 分析 |
| --- | --- |
| 缺少的資訊 | **改的目的**（可讀性？效能？修 bug？加功能？）、參數的業務意義（`t` 是會員等級還是客戶類型？）、**哪些不能變**（函式名稱、簽名、回傳型別、計算結果）、要不要測試、輸出要完整程式還是 diff |
| 可能誤解的方向 | 改名或改簽名（破壞呼叫端）；「順手」修改業務規則（例如把 `>` 改成 `>=`）；擅自猜參數意義；大改架構（引入類別、Enum、設定檔） |
| 品質問題 | 改完看起來漂亮但**呼叫端壞掉**、隱性的行為改變（回傳型別、浮點誤差）、每次問結果都不同、無法驗收 |

**實測證據**：原版提示詞產出的重構把 `calc` 改名成 `calculate_order_total`，模組裡**不再有 `calc`**（所有舊的呼叫端都會 `NameError`），回傳型別也從 `int` 變成 `float`（`calc(50,3,30)` 原本是 `1450`，變成 `1450.0`）。它還把 `t` 猜成「客戶類型」。→ `test_p1_before_breaks_interface` 證實。

### ②「這個 bug 怎麼修」

| 面向 | 分析 |
| --- | --- |
| 缺少的資訊 | **錯誤現象**（錯誤訊息／stack trace）、重現步驟與輸入、**期望行為**（空清單要回 0？None？拋錯？）、執行環境（Python 版本）、修改範圍限制 |
| 可能誤解的方向 | 修錯 bug（只修看得到的那一個）；自行決定錯誤語意（回 0 會讓「0 分」和「沒資料」混淆）；把修 bug 擴大成重寫＋加一堆驗證 |
| 品質問題 | 「修好」但行為不是你要的、範圍膨脹（scope creep）、症狀被掩蓋而根因沒處理、沒有測試證明真的修好 |

**實測證據**：原版輸出自己發明了規格——字串分數拋 `TypeError`、`True` 拋錯、`NaN` 拋 `ValueError`、`scores=None` 回 `None`。都很合理，但**沒有一項是需求**，程式長了一倍（2087 字 vs 1058 字）。核心修正碰巧和規格一致（`test_p2_fix_meets_spec[before]` 通過），這是運氣，不是提示詞的功勞。

### ③「寫個 API」

| 面向 | 分析 |
| --- | --- |
| 缺少的資訊 | 業務領域（什麼資源）、端點清單、框架與語言、儲存層、認證方式、錯誤格式、規模／行數、交付形式 |
| 可能誤解的方向 | 完全不同的領域（待辦清單？部落格？）、不同框架（Express／Flask／Next.js）、沒認證或認證寫死密鑰、過度設計（直接上 DB＋Docker） |
| 品質問題 | 產出無法使用、或 Claude 只能反問而**零產出**；團隊每人問出來的風格都不同 |

**實測證據**：原版提示詞的輸出是 **6 題反問、0 行程式碼**（764 字）。

## 任務 2：改寫提示詞（[角色] + [任務] + [限制] + [輸出格式]）

完整版存在 `prompts/ex01/p*-after.txt`（程式碼以 `{{file:...}}` 引用 `samples/`，兩個版本拿到完全相同的程式碼）。

### ① 改寫版

> 【角色】你是重視可讀性與可維護性的資深 Python 工程師。
> 【任務】重構下方 `calc` 函式（電商訂單金額計算）：p=單價、t=會員等級（1=一般會員、2=VIP、其他=非會員）、q=數量。目標是提升可讀性，**外部行為必須完全不變**。
> 【限制】保留 `calc(p, t, q)` 可用；魔術數字改具名常數；加型別提示與繁中 docstring；不引入第三方套件；不改任何計算結果（含 >1000 折抵 50）。
> 【輸出格式】1. 完整程式碼 2. 3~5 點改動說明 3. 3 個 assert 證明行為不變。

### ② 改寫版

> 【角色】你是擅長根因分析的 Python 除錯工程師。
> 【任務】修正 `average_score` 的 bug。
> 【現象】`average_score([])` 拋出 `ZeroDivisionError`（Python 3.14），上游偶爾有 `None`（缺考）。
> 【期望行為】空清單回 `None`；`None` 略過；全 None 回 `None`；其餘回四捨五入 2 位的平均。
> 【限制】只改這個函式、不加套件、保留函式名稱。
> 【輸出格式】1. 根因 1~2 句 2. 修正後程式碼 3. 4 個 assert（正常／空清單／含 None／全 None）。

> 技巧：多加了【現象】【期望行為】兩欄——除錯提示詞最關鍵的就是「實際 vs 期望」。

### ③ 改寫版

> 【角色】你是 Python 後端工程師，熟悉 FastAPI 與 REST 設計。
> 【任務】為使用者管理系統設計 RESTful API：列表（分頁）、單筆、建立、更新、刪除。
> 【限制】FastAPI + Pydantic v2；記憶體 dict 當儲存層；所有端點 JWT Bearer 認證（`Depends` 抽出，密鑰讀環境變數 `JWT_SECRET`）；錯誤遵循 RFC 7807；程式碼 120 行內。
> 【輸出格式】1. 端點一覽表 2. 單一 main.py 3. 3 行以內的啟動與測試指令。

## 結論

1. **改寫最大的價值在「不能變的東西」**：原版①在可讀性上做得不差，但它不知道 `calc` 有呼叫端，所以改名了——這種錯是靜默的，code review 時很容易漏。限制欄位就是把隱性需求變顯性。
2. **期望行為要寫出來**：②原版的修正「碰巧」符合規格，但多了一堆自己發明的規則；改寫後輸出短一半且完全可驗收。
3. **完全沒資訊時，好的 Claude 會反問而不是亂寫**（③原版）。這比亂寫好，但等於浪費一輪對話。
4. **限制不保證被遵守**：③的行數限制被打破，模型還自報錯誤行數 → 可量化的限制要用工具驗證（本練習用 pytest 抓到）。
5. 本實驗的原版輸出品質偏高，原因是子 claude 也讀到了使用者的全域 CLAUDE.md（已有大量品質規則）。在沒有 CLAUDE.md 的環境，原版提示詞的差距應會更大（未實測，見 NOTES.md）。
