# 練習 01 解答 — 5 個開發場景 Prompt 模板 + 共同模式

> 完整模板（含變數表、使用說明、版本紀錄）都已建成檔案，放在 `prompts/`，本檔是摘要＋模式分析。
> 範例素材統一用 `samples/order_utils.py`（含 `calc_total`、`average_price`，後者空清單會除以零）。

## 任務 1：5 個模板

### 1. 程式碼審查 → `prompts/review/code-review.md`
- **場景**：PR 送出前、接手別人程式碼時，依指定標準審查。
- **模板**：
  ```
  你是一位資深 {{language}} 工程師，負責審查團隊的程式碼。
  背景：這段程式用於「{{context}}」。
  請只依照以下標準審查：{{standards}}。
  規則：1. 指出行號/函式並說明為什麼 2. 分 🔴必改/🟡建議/🟢備註 3. 🔴附修正碼 4. 不評論標準以外項目
  程式碼：{{code}}
  輸出格式：一行總評 + 問題表格（嚴重度/位置/問題/建議）+ 🔴 修正碼
  ```
- **範例填入**：language=Python、standards=正確性, 錯誤處理, 邊界值、context=電商訂單金額計算、code=order_utils.py
- **預期輸出**：總評一行 → 表格（應抓到 `average_price` 空清單 🔴）→ 修正碼

### 2. 除錯助手 → `prompts/debug/error-analysis.md`
- **場景**：有 exception / 錯誤訊息、看不出原因。
- **模板**：
  ```
  你是一位擅長系統性除錯的工程師。請用「假設 → 驗證」的方式分析以下錯誤。
  錯誤訊息：{{error_message}}  相關程式碼：{{code}}
  觸發輸入：{{input}}  環境：{{environment}}  已試過：{{tried}}
  請依序回答：1. 根本原因 2. 輸入如何觸發（對應行）3. 修正碼＋預期行為 4. 回歸測試
  不要猜測沒有證據的原因；資訊不足時列出需要的資訊。
  ```
- **範例填入**：error_message=`ZeroDivisionError: division by zero`（實際跑 `average_price([])` 取得）、input=`items = []`、environment=Python 3.12 / Windows 10、tried=無
- **預期輸出**：四個編號段落

### 3. 寫測試 → `prompts/code/write-tests.md`
- **場景**：寫完函式或修 bug 前補測試。
- **模板**：
  ```
  你是一位重視測試品質的工程師。請用 {{framework}} 為下面的函式寫測試。
  函式（從 {{module_path}} import）：{{function_code}}
  期望行為：{{behaviors}}
  要求：1. 正常/邊界/錯誤三類 2. 測試名稱說明驗證內容 3. 不 mock 不必要的東西 4. 規格與實作衝突時加註解
  輸出格式：一個完整可執行測試檔 + 條列說明每個案例
  ```
- **範例填入**：framework=pytest、function_code=calc_total、behaviors=discount 0~100、空清單回 0、四捨五入 2 位
- **預期輸出**：`test_order_utils.py` 程式碼區塊 + 條列

### 4. 重構 → `prompts/code/refactor.md`
- **場景**：程式能動但難讀/重複/巢狀深。
- **模板**：
  ```
  你是一位 {{language}} 重構專家。目標：{{goals}}  限制（絕對不能改）：{{constraints}}
  規則：1. 外部行為完全相同 2. 標出重構手法名稱 3. 發現 bug 不要順手修，列在最後
  原始程式碼：{{code}}
  輸出格式：重構後程式碼 + 變更清單表（手法/位置/理由）+ 發現的問題
  ```
- **範例填入**：goals=可讀性、改用內建函式；constraints=函式名稱與參數、回傳 round(...,2)
- **預期輸出**：程式碼 + 表格 + 「發現的問題」（應指出 discount 範圍未檢查）

### 5. 解釋程式碼 → `prompts/writing/explain-code.md`（✅ 已用 `claude -p` 實跑）
- **場景**：把程式講給不同背景的人聽。
- **模板**：
  ```
  請把下面的程式碼解釋給「{{audience}}」聽。他們最想知道：{{purpose}}
  規則：1. 用對方熟悉的詞，專有名詞一句話白話解釋 2. 先做什麼→怎麼做→注意什麼 3. 至少一個具體數字例子 4. 長度：{{length}}
  程式碼：{{code}}
  輸出格式：三個小標題「做什麼 / 怎麼做（含例子）/ 注意事項」
  ```
- **範例填入**：audience=不寫程式的產品經理、purpose=折扣怎麼算、金額會不會算錯、length=250 字以內
- **實際輸出**：見 `runs/explain-code.output.md`。三段格式正確、用 100×2+50×1 打九折=225 元走一遍，並主動指出「折扣填 150 會變負數」。

## 任務 2：共同模式分析

把 5 個模板並排看，結構幾乎一樣，可以拆成三段：

| 位置 | 共同元素 | 5 個模板的實際寫法 |
| --- | --- | --- |
| **開頭** | ① 角色 ② 背景/目標 | 「資深工程師」「除錯工程師」「重構專家」「測試工程師」；解釋程式碼改用「聽眾是誰」代替角色。緊接著一句背景（用途、環境、症狀） |
| **中間** | ③ 輸入資料 ④ 具體指令（編號步驟）⑤ 限制/禁止事項 | 全部用**編號清單**寫指令；每個都有一條「不要…」：不評論標準外項目、不猜測無證據原因、不 mock、不順手修 bug、不講專有名詞不解釋 |
| **結尾** | ⑥ 輸出格式 ⑦ 長度/數量 | 全部明確指定「表格欄位」或「固定小標題」；有長度需求的放變數（`{{length}}`） |

觀察到的規律：
1. **變數集中在「背景」與「輸入資料」**，指令與格式是固定的——這正是模板可以重複用的原因。
2. **「限制」最有價值**：沒有「不要…」時，Claude 傾向做多（順手修 bug、附贈風格建議）。
3. **程式碼一律用 ``` 包住並放在指令後面**，避免程式碼裡的文字被當成指令。
4. **輸出格式越具體越好控**：實跑 explain-code 時，三段標題完全照做；但「250 字以內」只是軟限制，實際約 285 字（含標點）→ 長度需要更硬的寫法（見 ex02 進化機制）。

通用骨架：
```
[角色]你是一位 {{role}}。
[背景]{{context}}
[輸入]```{{input}}```
[指令]1. … 2. … 3. …
[限制]不要 …
[格式]輸出格式：…，長度 …
```
