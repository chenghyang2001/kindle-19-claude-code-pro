# 附錄 C 清單審查：ch15-sample（vulnerable／fixed）

- 審查對象：`ch15-sample/vulnerable/app.py`（V）、`ch15-sample/fixed/app.py`（F），行號皆指該檔
- 審查方式：人工逐行閱讀 ＋ bandit 1.9.4 ＋ 動態探測腳本 `answer/audit/probe_checklist.py`
- **只審查、不修改**：ch15-sample 的 11 個檔案時間戳與數量都和複製當下相同；所有工具都加上 `PYTHONDONTWRITEBYTECODE=1`，pytest 另加 `-p no:cacheprovider`
- 證據檔（`answer/reports/`）：

| 檔案 | 內容 |
| --- | --- |
| `exploit-demo.txt` | 漏洞版攻擊重現 |
| `pytest-fixed.txt` | 修復版測試，13 passed |
| `v7-assert-bypass.txt` | `python -O` 繞過 assert 權限檢查 |
| `probe-checklist.txt` | P1～P13 動態探測 |
| `probe-arg-injection.txt` | ping 參數注入 |
| `bandit-*.txt`／`bandit-*.json` | bandit 自動掃描 |

圖例：✅ 通過　❌ 不通過　➖ 不適用

## 總覽

| 版本 | ✅ 通過 | ❌ 不通過 | ➖ 不適用 |
| --- | :---: | :---: | :---: |
| vulnerable | 3 | 16 | 7 |
| fixed | 5 | 14 | 7 |

**結論**：第 15 章的修復版把 7 個**程式碼層**漏洞（注入、反序列化、弱雜湊、硬編碼密鑰、assert）都修好了，bandit 的 High／Medium 從 8 個降為 0 個。但附錄 C 大部分在檢查**身份驗證、授權、頻率限制**等架構層防護，這個範例本來就沒有這些機制，所以修復版在附錄 C 上淨增 2 項：#15、#19、#24 從不通過變成通過，但 #11 反而從通過變成不通過（改用耗時的 PBKDF2 後，出現了時間差列舉）。也就是說，「掃描器乾淨、測試全綠」不代表可以上線。
