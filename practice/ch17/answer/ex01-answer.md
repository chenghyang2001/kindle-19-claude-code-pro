# 練習 01 解答：分析現有 CLAUDE.md

評分對象：本 repo 根目錄 `CLAUDE.md`（只有「本專案例外」一節，共 2 段）。

## 任務 1：評分

| 評分維度 | 分數 | 理由 |
| --------- | :---: | ------ |
| 清晰度 | 4 | 規則具體：「主 Claude 直接寫檔」「不派 code-writer／code-qa／code-reviewer」「設定寫在 `.claude/settings.local.json`」都能直接照做。扣 1 分：「kindle-drill 快速模式」「三 agent 鐵律」是外部名詞，沒看過全域設定的新成員看不懂。 |
| 完整性 | 2 | 只講「流程例外」，沒有專案概述、目錄結構、技術堆疊、執行／測試指令。開發者最常問的「這是什麼？怎麼跑？怎麼測？」都答不出來。 |
| 簡潔性 | 5 | 兩段話、沒有重複或過時內容，每句都在改變 Claude 的行為。 |
| 可維護性 | 3 | 短所以好改；但沒有版本、日期、負責人，也沒有分節骨架，之後加內容時不知道放哪、也不知道何時該檢查是否過時。 |
| 有用性 | 3 | 對「流程」很有用（省掉每次被問複雜度、能直接寫檔），但對「程式碼品質」幫助是零：Claude 看完不會更懂這個 repo 的內容。 |
| **平均** | **3.4** | 是一份好的「覆寫規則」，但不是一份完整的專案 CLAUDE.md。 |

**改善建議**：保留現有兩段當作「## 流程例外」，前面補「## 關於此程式庫」（一段話）＋「## 目錄」＋「## 指令」，檔頭加版本／最後更新日期／負責人（附錄 B 的格式）。

## 任務 2：五種常見反模式

### 1. 過度詳細（把整本 API 文件塞進去）

壞例子：

```markdown
## API
### POST /api/users
參數：name (string, 必填, 1-50 字), email (string, 必填), age (int, 選填, 0-150) ...
回應 200：{ "id": ..., "name": ..., "createdAt": ... }
回應 400：...
（後面再 80 個端點）
```

問題：每次對話都把幾千 token 塞進 context，真正重要的規則被淹沒；而且 API 一改就過時。

改善：CLAUDE.md 只寫「位置＋慣例」，細節讓 Claude 需要時自己讀。

```markdown
## API
- 規格以 `openapi.yaml` 為準（需要時再讀，不要猜）
- 錯誤回應統一 `{ "error": string }`；驗證錯誤 400、未登入 401
```

### 2. 過時腐爛（記載已刪除的功能或路徑）

壞例子：`- 寄信邏輯在 src/mailer/legacy_smtp.js`（該檔半年前已被刪除，改成 `services/email.ts`）。

問題：Claude 會照著去找不存在的檔案，甚至「好心」重建一個舊檔。

改善：

- 檔頭加 `最後更新：YYYY-MM-DD`＋負責人，每季審查。
- 用腳本檢查文件裡提到的路徑是否存在（本次實作：`email-automation-演練/scripts/check_claude_md.py`，見 ex02 任務 3）。
- 刪目錄／改技術棧的 PR checklist 裡加一項「已同步 CLAUDE.md」。

### 3. 角色混亂（什麼都要讓 Claude 知道，但沒有優先順序）

壞例子：

```markdown
- 要注意效能
- 要寫測試
- 變數命名要好
- 安全很重要
- 程式要簡潔
- 要相容舊版
```

問題：六條平行，衝突時（例如「簡潔」對上「相容舊版」）Claude 不知道該犧牲哪個。

改善：明確排序，並說衝突時怎麼取捨。

```markdown
## 優先順序（衝突時由上而下）
1. 安全：不洩漏機密、不誤寄信
2. 正確性：測試全綠才算完成
3. 可讀性 > 效能（除非有 profiling 數據）
```

### 4. 禁止事項太多（只說「不要做 X」不說為什麼）

壞例子：

```markdown
- 不要用 jinja2
- 不要改 sender.py
- 不要用 print
- 不要加新檔案
```

問題：Claude 只能機械式遵守，遇到規則沒寫到的相似情況（例如 mako 範本引擎）無法類推；人類成員也會覺得規則武斷而跳過。

改善：每條禁止附原因，最好給替代做法。

```markdown
| 禁止 | 原因 | 改用 |
|------|------|------|
| 引入第三方範本引擎（jinja2 等） | 專案定位零依賴，clone 下來就能跑 | `string.Template` |
| 移除 dry-run 預設 | 誤寄給客戶無法收回 | 寄出前加確認提示 |
```

### 5. 無法驗證（規則太抽象）

壞例子：`- 程式碼要高品質、易維護`、`- 遵循最佳實踐`。

問題：沒有判斷標準，Claude 無法確認自己有沒有做到，審查者也無法指出違規。

改善：改成可檢查的條件。

```markdown
- 函式不超過 30 行；巢狀不超過 3 層
- 改完執行 `python -m unittest discover -s tests`，全綠才算完成
- 讀寫檔一律 `encoding="utf-8"`（可用 grep 檢查 `open(` 是否都有帶）
```
